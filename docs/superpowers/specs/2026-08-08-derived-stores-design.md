# Derived-сторы: дизайн

Дата: 2026-08-08
Статус: одобрено пользователем (диалоговый брейншторм), ожидает ревью спеки

## Контекст и цель

Сегодня derived-состояние (аналог `derived` из overmind.js) живёт в рукописном
классе `Derived` (`packages/signals_store_example/lib/ui/derived.dart`) — пучок
`computed()` над `AppStore`, создаваемый вручную. Цель — поднять механику на
уровень генератора: **полноценные сторы с доступом к корню дерева сторов**.

Ключевой сценарий (от пользователя): derived-сторы создаются **on-demand в любом
месте приложения**, где ссылки на корень нет. Пример: стейт экрана в стеке
навигации — экран открывается, создаётся derived-стор, корень при этом доступен
внутри стора. Экран закрывается — стор диспозится.

## Семантика

Derived-стор = **стор с собственным состоянием + доступ к корню**:

- собственные `abstract`-поля → реактивные `Signal`-поля (как в `@Store`);
  используются в т.ч. для параметров создания (`todoId` экрана);
- concrete-геттеры, читающие корень, → `Computed` (существующий детектор
  реактивности);
- доступ к корню — через самодекларируемый `abstract`-геттер `root`;
- `dispose()` для on-demand жизненного цикла.

Derived-стор **не является полем дерева** и не конструируется корнем — проблема
«курица-яйцо» отсутствует по построению. Монтирование derived как
concrete-поля-подстора в дерево остаётся возможным через существующий
pass-through механизм `@Store` (root резолвится лениво при первом доступе,
после регистрации корня) — не запрещаем, документируем.

## API

### Аннотация (signals_store_annotation)

```dart
class DerivedStore {
  const DerivedStore({required this.name});
  final String name;
}
```

Без параметра `from:` — единственный источник истины о типе корня это тип
abstract-геттера в impl (см. ниже). На одном классе — ровно одна аннотация
`@DerivedStore`; `@Store` и `@DerivedStore` на одном классе запрещены.

### Пользовательский код

```dart
@DerivedStore(name: 'TodoDetailsStore')
abstract class TodoDetailsStoreImpl {
  /// Корень дерева сторов. Маркер для генератора: реализация резолвится
  /// через StoreRootScope. Должен быть ровно один такой геттер.
  abstract AppStoreImpl get root;

  /// Собственное реактивное поле (параметр создания).
  abstract String todoId;

  /// Computed-геттер: читает корень → реактивен.
  Todo? get todo => root.projects.todos[todoId];
}
```

**Почему геттер, а не миксин/параметр аннотации:** source_gen не может вживить
член в исходный класс, а тела геттеров в impl должны анализироваться — `root`
обязан быть объявлен в самом impl. Вариант с миксином `RootedStore<R>` +
`from:` в аннотации рассматривался и отклонён: тип корня писался бы дважды,
плюс лишний API в рантайм-пакете. Вариант «только `from:` без объявления»
невозможен: идентификатор `root` в телах impl не разрешится (compile error).

**Почему геттер, а не поле:** синтаксис `abstract AppStoreImpl root;` (поле)
сегодня означает «Signal-поле стора» — root таким быть не должен (стабильная
ссылка, резолвится один раз). Поле, типизированное корневым impl, в
`@DerivedStore`-классе → валидационная ошибка «объявите root как
abstract-геттер».

### Генерируемый код

```dart
class TodoDetailsStore extends TodoDetailsStoreImpl {
  TodoDetailsStore({required String todoId})
      : todoId$ = Signal<String>(todoId,
            options: SignalOptions<String>(
                name: 'TodoDetailsStore.todoId'));

  final Signal<String> todoId$;

  @override
  String get todoId => todoId$.value;
  @override
  set todoId(String value) => todoId$.value = value;

  @override
  late final AppStoreImpl root = StoreRootScope.of<AppStoreImpl>();

  late final Computed<Todo?> todo$ = computed(() => todoRaw,
      options: ComputedOptions<Todo?>(name: 'TodoDetailsStore.todo'));

  @override
  Todo? get todo => todo$.value;
  @override
  Todo? get todoRaw => super.todo;

  void dispose() {
    todoId$.dispose();
    todo$.dispose();
  }
}
```

- `root` — `late final`, резолвится лениво при первом обращении (внутри
  вычисления computed). К этому моменту корень уже зарегистрирован.
- `dispose()` генерируется только для derived (экранный lifecycle:
  `State.dispose()` → `store.dispose()`). Корневые сторы не меняются
  (app-lifetime).
- Правила полей/геттеров/конструктора — как у `@Store` (abstract-поля →
  Signal, concrete-поля → pass-through, reactive-геттеры → Computed,
  коллизии имён — существующий `_checkNameCollisions` + учёт `root`/`dispose`).

## StoreRootScope (runtime, signals_store)

Zone-aware реестр корня через `Expando` (zone-values иммутабельны — положить
значение в зону без форка нельзя, поэтому ключ — объект самой зоны):

```dart
class StoreRootScope {
  static final Expando<List<Object>> _byZone = Expando('StoreRootScope');

  /// Регистрирует корень, привязывая к Zone.current. Повторная регистрация
  /// корня того же типа в той же зоне — заменяет (hot reload, setUp в тестах).
  static void register(Object root);

  /// Резолвит корень по типу: текущая зона → Zone.root (глобальная) →
  /// StateError с понятным текстом. Поиск — `is T`-скан регистраций зоны.
  static T of<T>();
}
```

- **Приложение:** весь код живёт в одной зоне (root-зона или зона
  `runZonedGuarded`) → регистрация и резолв консистентны.
- **Тесты:** package:test создаёт зону на тест → регистрация в одном тесте
  невидима в другом, `reset()`/`tearDown` не нужны.
- **Авторегистрация:** конструктор сгенерированного **корневого** стора
  получает тело `{ StoreRootScope.register(this); }` (сейчас у конструктора
  только initializer-list). Некорневые сторы не меняются. `main.dart` не
  меняется вообще.

### Эмпирические проверки ДО реализации (обязательные задачи плана)

По принципу verify-before-planning — гипотезы зон проверяются кодом:

1. `Zone.current` различается между тестами в package:test и flutter_test
   (иначе изоляция через Expando не работает — нужен fallback-дизайн).
2. Резолв внутри `testWidgets`-билда видит регистрацию из тела теста
   (зона биндинга может оказаться предком зоны тела → резолв уйдёт в
   глобальный реестр; тогда для виджет-тестов документируем глобальную
   регистрацию).
3. Сценарий `runZonedGuarded` в `main()`: регистрация и резолв в одной зоне.

## Root-детекция и смена root-статуса

Root-статус — свойство **типа**, пересчитывается при каждой генерации:
impl — корень, если его тип **не встречается среди типов полей** других impl
библиотеки (и `@Store`, и `@DerivedStore`; граф containment,
библиотека-локально). Abstract root-геттер — не поле, на containment не влияет.

- **Параллельный второй корень** (StoreX — отдельное дерево): StoreA остаётся
  корнем, оба конструктора регистрируют, `of<StoreAImpl>()` работает — derived
  не ломаются.
- **Поглощение** (в StoreXImpl появилось поле типа StoreAImpl): StoreA теряет
  root-статус → его конструктор теряет авторегистрацию, StoreX получает.
  Генерация derived со stale-типом root **падает с ошибкой кодогенерации**:
  «root-геттер типизирован StoreAImpl, который содержится в StoreXImpl и не
  является корнем; перетипизируйте на StoreXImpl». Тихого неправильного
  резолва не бывает: без валидации `of<StoreAImpl>()` в рантайме бросил бы
  StateError (инстанс StoreX содержит StoreA, но не является им).
- **Ограничение:** один и тот же impl-тип не может быть одновременно корнем
  одного дерева и подстором другого. Exotic-кейс; резолв в подсторы
  (рекурсивный обход полей корней) осознанно не делаем (YAGNI), поведение
  задокументировано.

## Изменения в генераторе

1. Новый `TypeChecker` для `@DerivedStore`; обработка в том же проходе, что
   `@Store` (общий пайплайн: поля, геттеры, конструктор, коллизии).
2. Детектор реактивности: имя root-геттера добавляется в reactive-базу
   (его тип — impl ∈ storeImplNames → реактивен). Геттеры, читающие `root.*`,
   становятся Computed существующим фикс-пойнтом. Новых механизмов
   реактивности не требуется.
3. Root-детекция: построение графа containment по типам полей всех impl
   библиотеки; корни получают тело конструктора с авторегистрацией.
4. Валидации (понятные ошибки `InvalidGenerationSource`):
   - `@DerivedStore` только на abstract-классе;
   - ровно один abstract-геттер, типизированный корневым impl (= root-слот);
     ноль — ошибка «объявите root»; больше одного — ошибка;
   - тип root-геттера — @Store-impl и именно корень (не подстор и не
     `@DerivedStore`-impl: derived-of-derived не поддерживается, корень
     derived — всегда корень `@Store`-дерева);
   - поле (не геттер), типизированное корневым impl → ошибка «объявите как
     abstract-геттер»;
   - запрет named-конструкторов (как у `@Store`);
   - проверка «у @Store нет полей» к derived **не применяется**: derived без
     собственного состояния (только root + геттеры) валиден;
   - коллизии имён с именем root-геттера, `dispose`, `*Raw`, `*$`.
5. v1-ограничения (ошибки с понятным текстом): без type-параметров и
   `abstract: true` для derived; корень и derived — в одной библиотеке.

## Тестирование

- Юнит-тесты derived: тест создаёт `AppStore(...)` (авторегистрация
  привязывается к зоне теста) → создаёт derived → assert. Изоляция — через
  зоны, без `tearDown`.
- Подмена корня: `StoreRootScope.register(fakeExtendsAppStoreImpl)` — резолв
  по `is T` найдёт фейк.
- Тесты генератора: contains-матчеры + обязательный `dart analyze` на
  сгенерированном выводе (helper `_expectCompiles` — проектный принцип
  «codegen tests must compile»).
- Эмпирические проверки зон — отдельные задачи до реализации (см. выше).

## Миграция примера

Рукописный `Derived` в `ui/derived.dart` заменяется generated derived-стором
(или несколькими) — showcase в example-пакете. Консистентно с архитектурными
гайдлайнами: derived-сторы отвечают «как отобразить», живут в UI-слое.

## Отклонённые альтернативы

- **Миксин `RootedStore<R>` + `from:` в аннотации** — тип корня дважды, лишний
  runtime-API. Заменено самодекларируемым abstract-геттером.
- **`@Store(derived: true)`** — размытый контракт одной аннотации на два
  режима; менее очевидные ошибки пользователя.
- **Вывод derived по структуре без аннотации** — магия, ломает легальный
  сегодня pass-through concrete-поля типа корня.
- **Монтирование derived как поля корня с авто-созданием корнем** — не закрывает
  главный сценарий (создание on-demand в месте без ссылки на корень); оставлено
  как опция через существующий pass-through.
- **Резолв в подсторы (рекурсивный обход)** — YAGNI.
- **zone-values с форком зон (`runIsolated`)** — не нужно: Expando по
  Zone.current даёт изоляцию без форков.
